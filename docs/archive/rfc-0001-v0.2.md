## 1. 摘要

本方案在**不主动改变现有功能、站点匹配和权限行为**的前提下，将 5 个用户脚本迁移到统一的 UI 和工程规范中，并补齐基本的测试、构建与发布能力。

本次重构遵循三条原则：

1. **先验证行为，再迁移实现。** 每个脚本都要有核心行为清单和可重复的回归检查。
2. **只抽取真实重复的能力。** 共享模块以至少两个脚本确实需要为准，不提前建设通用框架。
3. **工具以实际收益决定是否采用。** 新工具必须解决现有痛点；小规模验证不通过，就保留现有方案。

关键决策如下：

- **D1 构建：** 先用不超过 0.5 人日验证 `vite-plugin-monkey`。只有它能可靠输出单文件、保留元数据与权限、兼容现有 UI 子模块，并显著改善开发体验时才替换当前构建脚本；否则继续使用现有 Vite 构建链路。
- **D2 版本：** 各脚本 `package.json` 的 `version` 是版本唯一来源，构建时注入 `@version`。初期使用轻量版本脚本和 CHANGELOG，不强制引入 Changesets；后续若跨包版本协调成为实际负担，再评估引入。
- **D3 共享内核：** 建立 `packages/shared`，优先统一 GM API 和重复的设置读写。DOM/SPA 工具、日志等只有在确实重复时再纳入；暂不为 i18n 或通用迁移框架预先设计抽象。
- **D4 发布：** CI 构建并归档产物、CHANGELOG 和 SHA-256；Greasy Fork 更新仍由维护者在已登录的浏览器中确认提交。回滚通过重新发布上一版稳定代码并使用更高的新版本号完成。

预计总工期仍按 **18–20 人日初估**，不是承诺值。P0 和构建验证结束后，按实际迁移难度重新估算剩余工作。每阶段结束均应停在可构建、可检查的稳定点。

## 2. 背景与问题

### 2.1 当前基础

仓库已采用 npm workspaces 管理 5 个脚本包；`packages/userscript-ui` 通过 git submodule 固定到具体提交；`tools/build.mjs` 提供 Vite IIFE 构建骨架；`tools/sync.py` 负责从 Greasy Fork 反向同步。5 个脚本的线上原版保存在各包 `legacy/` 下，尚未迁入 `src/`。

### 2.2 现状数据

统计口径：`legacy/*.user.js` 去掉元数据块后的正文。

| 指标 | 当前值 | 说明 |
| --- | ---: | --- |
| 脚本数 | 5 | — |
| 代码量 | 3546 行 / 126 KB | JavaScript，无类型 |
| Shadow Root | 0 | UI 直接操作宿主页面 DOM |
| 全局样式注入 | 3 个脚本 | 使用 `GM_addStyle` 或 `<style>` |
| `!important` | 398 处 | super-drag 215、input-autofill 183 |
| 硬编码颜色 | 34 种 | 无统一 Token |
| `z-index` 声明 | 7 处 | 可能与宿主页面层级冲突 |
| `innerHTML` | 13 处 | 需要逐处确认数据来源与安全性 |
| GM API 风格 | 混用 | 同步 `GM_*` 与异步 `GM.*` 并存 |
| 自动化测试 | 0 | — |
| 类型检查 / Lint | 0 | — |

### 2.3 问题与处理方向

| 编号 | 问题 | 处理方向 |
| --- | --- | --- |
| P1 | 浮层、面板、提示的样式和交互不一致 | 统一使用现有 `userscript-ui` 能力；组件缺口先确认是否值得补齐 |
| P2 | 样式进入宿主页面，`!important` 较多 | 将自有 UI 迁入 Shadow DOM，删除不再需要的全局样式；不以机械清零为目标 |
| P3 | 设置读写和 GM API 封装重复 | 提取经过至少两个脚本验证的共用实现 |
| P4 | 没有自动化质量门禁 | 建立 lint、类型检查、测试和构建检查 |
| P5 | 版本信息分散 | 以各脚本的 `package.json` 为版本来源，构建产物做一致性校验 |
| P6 | 发布资产和回滚步骤不清晰 | 按版本归档最终产物、校验和与变更说明 |
| P7 | HTML 注入 API 缺少统一约束 | 默认用 `textContent` 和 DOM API；禁止把不可信内容拼入 HTML 字符串 |

## 3. 目标与非目标

### 3.1 目标

| 编号 | 目标 | 验收方式 |
| --- | --- | --- |
| G1 | UI 风格和生命周期统一 | 有可见 UI 的脚本使用 `@ui` 组件并挂载在各自的 Shadow Root 中 |
| G2 | 重复能力只有一个维护入口 | 已确认需要共享的 GM 适配和设置读写归入 `packages/shared` |
| G3 | 变更有自动检查 | PR 至少运行静态检查、测试和构建；检查失败不能合并 |
| G4 | 每次发布可追溯 | 归档版本、最终 `.user.js`、SHA-256 和变更说明；完成一次回滚演练 |
| G5 | 开发体验可用 | 可以针对单个脚本构建与调试；目标全量构建时间不超过 15 秒 |

### 3.2 非目标

- 不新增用户可见功能，不主动修改匹配站点或权限；确需删除权限时必须有代码依据并单独核对。
- 不引入 React、Vue、Tailwind 等运行时框架，不引入远程运行时资源。
- 不将用户脚本改成后台服务或独立 Web 应用。
- 不修改 Greasy Fork 账号与脚本 ID。
- 不在本次工作中重做全部业务规则，也不为了测试覆盖率而重写与本次目标无关的代码。

### 3.3 运行与兼容约束

- 发布产物是单文件 `.user.js`，元数据块位于文件开头。
- 运行时不依赖额外远程脚本或样式；CSS 内联到产物。
- 自有 UI 使用 Shadow DOM 隔离，不向宿主页面注入全局 CSS。
- 目标浏览器基线暂定为 Chromium 111+；其他浏览器不承诺自动化覆盖。若实际用户范围要求 Firefox 等浏览器，需在正式迁移前重新确认构建目标与兼容性范围。
- 元数据校验接受 `@match` 或 `@include` 等合法匹配声明，不假定每个现有脚本都必须使用 `@match`。

## 4. 关键决策与取舍

### D1：构建工具先做验证，不预设替换结论

`vite-plugin-monkey` 提供元数据注入、GM API 权限收集和开发期热更新等能力，但共享 GM 封装、动态调用和现有子模块可能影响自动权限收集的准确性。**不能仅凭功能列表就认定它能直接替换现有构建脚本。**

0.5 人日 spike 使用一个结构简单、包含真实 `@ui` 与 `shared` 调用的脚本验证：

1. 最终产物为单文件，元数据完整且位置正确。
2. 原有 `@match`、`@grant` 等行为未被意外改变；自动收集的权限可以逐项核对。
3. 不依赖额外远程资源，能正确打包 CSS、子模块和共享代码。
4. 开发期调试确实比当前方式省步骤，而不是仅能启动 Vite 服务。
5. 现有 `tools/build.mjs` 可以明显简化或删除，且维护成本没有转移到另一套复杂配置中。

全部通过才替换。若自动权限收集不可靠，可以继续显式维护 `@grant`，不必为了自动推断而改变 GM 封装方式。

### D2：版本管理先保持轻量

- 各脚本 `package.json` 的 `version` 是唯一版本来源。
- `userscript.meta.ts` 保存静态元数据，不手写 `@version`。
- 构建后校验产物中的 `@version` 与包版本一致。
- 初期由统一脚本负责版本提升、CHANGELOG 更新和 tag 前检查；不手工维护多个互相独立的版本字段。
- 暂不强制使用 Changesets。若之后需要在一个变更中协调多个脚本包的版本与变更日志，再引入 Changesets。

### D3：共享内核只收纳已验证的重复逻辑

首批候选：

- `gm`：统一 GM API 的调用方式和 Promise 行为，明确同步/异步差异。
- `storage`：统一设置读写、默认值和错误处理；只有确有旧数据结构迁移需求时才引入 schema 版本与迁移函数。
- `dom`：只收纳至少两个脚本共用且接口稳定的等待元素、监听器清理等工具。
- `log`：若统一日志确实能减少重复，再提供轻量封装。

暂不预建 i18n、设置面板生成器或通用插件系统。任何模块都不应只是把单次调用简单包一层；共用 API 需有清晰契约和测试。

### D4：发布自动化到人工确认前为止

CI 负责验证、构建、生成校验和并归档 Release。Greasy Fork 不提供直接发布 API，预填更新仍需登录会话，并由维护者在网页中检查和提交。因此不在 CI 中模拟登录、保存会话 Cookie 或自动提交发布。

## 5. 目标架构

### 5.1 依赖关系

```text
scripts/<slug>
   ├── packages/shared          # GM、设置读写、确有重复的 DOM 工具
   └── packages/userscript-ui   # Shadow DOM 组件、Token、主题与 UI 生命周期

约束：scripts 可以依赖 shared 和 userscript-ui；两者不互相依赖。
```

### 5.2 包职责

| 包 | 职责 | 不应承担的责任 |
| --- | --- | --- |
| `packages/userscript-ui` | 共用组件、Token、主题、UI 生命周期；继续作为只读子模块锁定到具体 commit | GM API、站点业务、设置数据持久化 |
| `packages/shared` | 经多个脚本验证的 GM、storage 和通用工具 | UI 元素、具体站点逻辑、未经需求验证的通用框架 |
| `scripts/<slug>` | 站点适配、业务规则、设置 schema、UI 组合 | 跨脚本直接 import 其他脚本、复制已有共享实现 |

### 5.3 单脚本目录

```text
scripts/<slug>/
├─ userscript.meta.ts     # 静态元数据，不包含版本号
├─ package.json           # 包名、唯一 version 来源及脚本命令
├─ src/
│  ├─ main.ts             # 启动、组合依赖、注册生命周期清理
│  ├─ settings.ts         # 本脚本设置、默认值；需要时定义迁移
│  ├─ ui/                 # 使用 @ui 组件的组合逻辑
│  └─ features/           # 站点业务；纯逻辑优先
├─ tests/                 # 关键行为与回归测试
└─ legacy/                # 迁移对照；通过验收后删除
```

`settings.ts`、`ui/` 或 `features/` 不要求每个脚本都机械创建：没有实际内容的目录不必保留。

### 5.4 构建和产物校验

```text
静态元数据 + package.json version + src/
                    │
                    ▼
               Vite 构建
                    │
                    ▼
             dist/<slug>.user.js
                    │
                    ▼
       元数据 / 单文件 / 体积 / SHA-256 校验
                    │
                    ▼
          GitHub Release 归档
```

- 构建目标应与第 3.3 节声明的浏览器基线一致，不把语法转换等同于 API 兼容性保证。
- 默认保留可审阅的构建输出；如产物体积或发布平台有明确需要，再启用压缩。
- `dist/` 不提交到仓库；正式产物以对应 GitHub Release 资产为准。
- 校验必须针对本次重新构建的产物，不能复用工作区里可能过期的文件。
- npm workspaces 内部依赖使用 npm 识别的标准包版本范围，并由 workspace 自动链接；不要直接假定 `workspace:*` 是可用的 npm 依赖协议。

### 5.5 元数据与 GM 权限

静态元数据至少校验名称、描述、命名空间、匹配规则及权限声明。匹配规则须符合 Greasy Fork 要求，不能只校验 `@match` 是否为空。

GM 权限以实际使用为准，但迁移期间要先保留线上行为：

1. 记录 legacy 的匹配规则、权限和关键运行行为。
2. 逐步迁移后，将实际 GM API 调用与 `@grant` 对照。
3. 只有确认某项权限不再需要，才在单独检查后删除。
4. 自动权限收集只有在 D1 验证可靠时启用；否则显式声明权限并由检查脚本发现不一致。

### 5.6 运行时约定

- **UI 生命周期：** 有 UI 的脚本创建一个 UI 实例；主动卸载或替换时调用 `destroy()` 并清理监听器、定时器与观察器。不要把某个浏览器事件当作所有用户脚本管理器都支持的通用卸载通知。
- **SPA：** 路由变化时优先更新业务状态；只有页面结构确实要求时才重新挂载 UI，避免重复插入根节点。
- **主题：** 挂载时显式传入 `light | dark | system`。`system` 跟随系统偏好，不读取宿主网站主题，除非某脚本已有明确需求。
- **设置：** 保留现有设置键和数据格式。只有数据结构变更时才添加迁移逻辑；迁移失败时记录错误并安全回退，不静默覆盖可恢复的数据。
- **GM 适配：** 兼容当前实际支持的同步/异步 GM API，统一错误语义和返回类型。不要在没有使用场景时把所有 GM API 全部封装一遍。
- **日志：** 使用统一前缀；生产环境默认只输出 warn/error，排查问题时允许按需启用 debug。

## 6. 工程规范与测试

### 6.1 基础代码规范

- TypeScript `strict`，开启 `noEmit` 类型检查；业务代码避免 `any`，边界类型不明确时优先使用 `unknown` 并进行收窄。
- ESLint flat config、Prettier；沿用 `userscript-ui` 已有规则，尽量共用现成配置，不另建一套相似规则。
- 用户输入或站点内容默认通过 `textContent`、属性设置或 DOM API 插入。禁止将不可信数据拼接进 `innerHTML` 等 HTML 解析接口；确需使用时必须限定为可信静态模板并说明原因。
- `==`、`eval`、`new Function` 等按现有设计体系规则禁止。
- 使用已有规范：单引号、100 列、尾逗号、LF；包目录使用 kebab-case，函数使用 camelCase，存储键采用 `<slug>:<area>.<key>`。
- Agent 生成代码仍需通过相同检查；不要通过放宽规则来消除迁移中的错误。

### 6.2 测试策略

测试的优先级是**关键行为、回归和错误路径**，覆盖率只作为辅助信号。

| 层级 | 工具 | 测试范围 | 门槛 |
| --- | --- | --- | --- |
| 单元 | Vitest + happy-dom | `shared` 公共 API、设置读写、URL/规则匹配/文本清洗等纯逻辑 | 关键分支和错误路径有测试；初始覆盖率目标约 80%，不为数字写无价值测试 |
| 集成 | Vitest + happy-dom | UI 组装、设置读写、初始化和清理 | 每个脚本至少覆盖一条核心流程 |
| 端到端 | Playwright + Chromium | 本地 fixture 页面、关键交互、深色主题和站点 DOM 变化 | 发布前跑全量；PR 阶段先跑全量，若耗时明显超标再按受影响包优化 |
| 产物检查 | Node 脚本 | 元数据、单文件、版本、权限清单、体积和 SHA-256 | 任何不符合发布要求的产物都失败退出 |

E2E 使用本地 fixture 和路由拦截，不依赖真实账号或不稳定的线上数据。优先复用设计体系已有的测试工具、夹具和约定，不额外搭建第二套视觉回归系统。

P0 的行为基线不等于把整份旧代码全部做成快照。应为每个脚本记录核心用例、输入输出和必要的人工检查步骤；纯逻辑在迁移时补成单元测试，交互行为用 fixture 或可重复的验收清单覆盖。

### 6.3 提交与分支

- `main` 受保护，使用短期分支：`feat/<slug>/<topic>`、`fix/<slug>/<topic>`。
- Conventional Commits：`feat|fix|refactor|docs|test|chore|build(scope): subject`；scope 为脚本 slug 或包名。
- PR 必须通过 `npm run check`。单人维护时可以 CI 结果代替独立 reviewer，但重构 PR 必须核对该脚本的行为对照清单。
- 初期通过 PR 模板提示提交类型和变更影响，不额外引入 commit-msg hook 或强制 commitlint；若提交信息质量确实影响版本生成，再增加自动校验。

### 6.4 CI 流水线

| 阶段 | 内容 | 目标耗时 |
| --- | --- | --- |
| 静态检查 | lint、format check、`tsc`、元数据校验 | ≤ 2 min |
| 单元/集成 | Vitest | ≤ 2 min |
| 构建与产物检查 | 全量构建、元数据、体积校验 | ≤ 2 min |
| E2E | Playwright + Chromium | ≤ 8 min |
| 发布 | tag 校验、构建、校验和、Release 资产 | ≤ 3 min |

这些时间是观察目标，不是为了满足数字而拆出复杂的流水线。若实际总耗时稳定在可接受范围内，不引入缓存、矩阵或按路径选择测试等优化。

## 7. 发布与回滚

### 7.1 发布流程

1. 确认变更范围、核心行为检查结果和 CHANGELOG 条目。
2. 通过统一脚本提升对应脚本的 `package.json` 版本，并检查变更日志；版本号不在多个文件中分别手改。
3. 合并并打 tag：`<slug>@<version>`。
4. CI 根据 tag 重新构建，校验元数据与版本、生成 SHA-256，并将 `.user.js`、校验和及 CHANGELOG 归档至 GitHub Release。
5. 维护者使用 Greasy Fork 的预填更新流程，在已登录的浏览器中核对脚本内容、版本和权限后手动提交。
6. 记录 Greasy Fork 发布链接、版本和必要的手动检查结果。

如果预填流程需要单独的本地辅助工具，该工具不得保存或上传会话 Cookie；如果实现成本或稳定性不佳，直接使用 Greasy Fork 页面更新，不为“一条命令”目标额外构建复杂工具。

### 7.2 回滚规则

- 回滚源使用 GitHub Release 中上一版已验证的 `.user.js`。
- **不要把 `package.json` 版本号降回旧版本。** 将上一版稳定代码重新构建或取回后，以新的、更高的版本号发布，避免版本倒退造成更新问题。
- 保留回滚提交和原因说明；对已发布代码的回退仍需通过构建、产物校验和 Greasy Fork 人工确认。
- 完成一次演练，目标是在步骤明确、权限正常的前提下 10 分钟内恢复到可发布状态。

## 8. 实施路线

| 阶段 | 范围 | 主要产出 | 退出标准 | 初估人日 |
| --- | --- | --- | --- | ---: |
| P0 基线 | 工具链、行为清单和最小回归测试 | ESLint/Prettier/tsc/Vitest、CI、5 个脚本的行为对照表、体积基线 | `npm run check` 可运行；关键行为已有可重复检查 | 2 |
| P1 共享内核与构建验证 | 先实现实际重复的 GM/storage 能力；完成构建 spike | `packages/shared` 首批模块与测试；D1 决策记录 | 共用 API 有测试；构建方案明确且可复现 | 4–5 |
| P2 UI 与业务迁移 | 分脚本迁移到 `src/`，使用 `@ui` 并验证行为 | 每个脚本可独立构建、测试与检查 | 5/5 脚本通过行为对照；无宿主全局样式注入 | 8–9 |
| P3 发布流程 | 版本脚本、Release、校验和、回滚文档 | 完整发布流程与回滚演练 | 成功发布一次测试版本或正式版本，并完成回滚演练 | 2 |
| P4 收尾 | 清理、文档、复盘 | 删除已无用途的 `legacy/`，更新 README 和架构说明 | 文档反映真实实现，仓库无未解释的迁移残留 | 1 |

迁移顺序先选容易验证的脚本，再处理复杂交互：`capture-links` → `selection-copy` → `youtube-transcript-copy` → `input-autofill` → `super-drag`。完成前两个后复盘共享接口是否合适；如果早期脚本表明某个抽象没有实际复用价值，就调整接口，不要为保持原架构图而硬塞进 `shared`。

每迁移一个脚本都要完成：

1. 记录并核对原版的站点匹配、权限、设置和核心行为。
2. 迁移并运行自动化测试、构建与产物检查。
3. 对照原版执行关键手动流程，确认没有无意的功能变化。
4. 单独提交，确保 `main` 随时保持可构建。

P0 不要求先把所有业务代码改造成可测试模块。先把行为写清楚，再在迁移相应功能时补充单元测试。

## 9. 验收标准

| 维度 | 验收标准 |
| --- | --- |
| UI 一致性 | 所有实际存在的面板、浮层、提示均使用 `@ui`；不为没有 UI 的功能额外创建 UI |
| 样式隔离 | 自有 UI 挂载在 Shadow Root；不向宿主页面注入全局样式 |
| 安全 | 不把不可信内容拼接进 HTML 解析接口；剩余 HTML sink 必须有可信来源和明确理由 |
| 类型 | `tsc --noEmit` 通过，`strict` 生效 |
| 测试 | 各脚本核心流程可重复验证；共享 API 的关键成功、失败和边界路径有测试 |
| 体积 | 初次迁移后记录实际 raw/gzip 基线；暂以单脚本 80 KB raw / 25 KB gzip 为预警上限，只有实测确认合理后才作为硬门槛 |
| 构建 | 全量构建目标 ≤ 15 秒；构建输出为单文件，元数据在开头 |
| CI | 静态检查、测试、构建均通过；总耗时作为监控指标，不通过降低测试质量来压缩 |
| 发布 | 每个版本有 `.user.js`、SHA-256、CHANGELOG 与版本记录；Greasy Fork 更新经人工确认 |
| 回滚 | 完成演练；稳定代码以更高新版本号重新发布，目标 ≤ 10 分钟 |

`!important` 和 `innerHTML` 不以全仓库机械归零作为目标：迁移应删除因宿主样式污染而存在的冗余声明，并阻断不可信 HTML 注入；确有必要的局部例外必须易于审查、范围清晰且有注释。

## 10. 风险与应对

| 编号 | 风险 | 应对措施 |
| --- | --- | --- |
| R1 | 重构改变现有行为 | 先记录行为；分脚本迁移；每个脚本完成自动检查和人工对照后再合入 |
| R2 | `@ui` 缺少必要组件 | 先确认现有组件无法组合实现；必要时单独补齐上游组件，避免临时复制一套样式 |
| R3 | 子模块升级导致构建失败 | 固定 submodule commit；升级单独提交并运行完整检查 |
| R4 | 构建插件无法正确收集 GM 权限或 HMR 收益有限 | 通过 spike 判定；不通过就保留当前构建链路 |
| R5 | 发布仍需要人工步骤 | 将自动化边界限定在构建和归档；人工核对列入发布清单，不模拟登录 |
| R6 | 迁移范围膨胀 | 不新增用户功能；共享模块以实际重复为依据；新需求另行评估 |
| R7 | 工期超出初估 | P0/P1 后重估；按单脚本交付，不把尚未迁移的脚本阻塞在同一大 PR 中 |
| R8 | 不同浏览器行为不一致 | 明确 Chromium 111+ 为正式基线；对其他浏览器仅做尽力冒烟，用户范围变化时再扩展自动化 |

## 11. 灰度与暂停条件

先发布 `capture-links`，执行核心流程检查，并观察一周内可见的反馈。没有收到反馈不能等同于没有问题；灰度期间以可复现测试和实际功能检查作为主要依据，安装量变化只作辅助信息。

出现以下任一情况时，暂停后续迁移并评估回滚：

- 目标站点上核心功能出现可复现的失效；
- UI 被宿主页面样式显著破坏或出现重复挂载；
- 设置丢失、权限异常或数据迁移失败；
- Greasy Fork 出现集中且可复现的错误反馈。

项目没有运行时遥测，不能以“没有告警”作为安全证据。回滚按第 7.2 节执行，并记录复现步骤和修复条件。
